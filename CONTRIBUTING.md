# Bring back a result

Start at [p(doom)](https://aaron-alderman.github.io/p-doom/). Pick one claim and state a proposition you can actually test. The source wording and your proposition both travel with the submission.

- For a proof, give the assumptions and a derivation another reader can check. For an empirical result, give the data, method, controls, and the replay command or procedure.
- For a clean kill, give a counterexample or a failed test and state exactly what it defeats. A counterexample defeats a universal claim. A failed search for a witness leaves a possibility open unless you can exhaust the declared model.
- If the trail is blocked, name the smallest missing input and how obtaining it would change the test.

Use **Prepare public submission** to generate the issue from your notebook. GitHub is public. Include only material you can share. For long drafts, copy the issue text from the notebook and paste it into GitHub. You can attach a proof, counterexample, data or replay output to the issue. A downloaded JSON packet gives reviewers a portable record of your inputs and their source identities.

Reviewers check the exact claim, scope, independence of the evidence, and replay. Record one disposition in the issue discussion: supported within scope, defeated within scope, needs revision, or blocked on a named input. Include a reason and the next step or reopening condition. The issue record is a review proposal and discussion. Changes to the dossier require a separate corpus decision.
